# 多 Agent 编排方法论

> 定义 Agent 间的上下文传递协议、错误恢复策略和级联失败处理，确保多 Agent 协作的可靠性。

---

## 1. Agent 间上下文传递协议

### 1.1 上下文类型

| 上下文类型 | 说明 | 传递方式 | 示例 |
|-----------|------|----------|------|
| **文档上下文** | FS/UA/RTL 等文档路径和版本 | 文件路径引用 | `ds/doc/fs/data_adpt_FS_v2.0.md` |
| **决策上下文** | 设计决策和理由 | ADR 文件引用 | `ds/doc/pr/ADR-001_fifo_depth.md` |
| **约束上下文** | PPA/CDC/功耗等约束 | 约束表传递 | `PPA: area < 50kGates` |
| **状态上下文** | 当前执行状态和进度 | 中间状态文件 | `{module}_intermediate_state_v{ver}.json` |
| **问题上下文** | 待确认问题和阻塞项 | 问题清单 | `[ARCH-QUESTION] FIFO 深度待确认` |

### 1.2 上下文传递格式

Agent A 调用 Agent B 时，必须传递以下结构化上下文：

```json
{
  "from_agent": "chip-fs-writer",
  "to_agent": "chip-microarch-writer",
  "timestamp": "2026-05-13T10:30:00",
  "context_type": "handoff",
  "payload": {
    "document_paths": [
      "ds/doc/fs/data_adpt_FS_v2.0.md"
    ],
    "decisions": [
      {"id": "ADR-001", "decision": "异步 FIFO 深度 16", "status": "accepted"}
    ],
    "constraints": [
      {"type": "PPA", "key": "area", "value": "< 50kGates"},
      {"type": "CDC", "key": "strategy", "value": "async_fifo"}
    ],
    "open_questions": [
      {"id": "Q-001", "question": "ECC 是否需要？", "blocker": false}
    ],
    "pending_items": []
  }
}
```

### 1.3 上下文验证规则

| 验证项 | 规则 | 失败行为 |
|--------|------|----------|
| **文档存在性** | 所有引用的文档路径必须存在 | 暂停，报告缺失文档 |
| **版本一致性** | 引用的文档版本必须是最新的 | 警告，确认是否使用最新版 |
| **决策完整性** | 所有 ADR 状态必须是 accepted/rejected | 暂停，等待决策确认 |
| **约束合理性** | 约束值必须在合理范围内 | 警告，确认约束值 |
| **问题闭环** | blocker=true 的问题必须有解答 | 阻塞，等待问题解答 |

## 2. Agent 协作模式

### 2.1 协作模式定义

| 模式 | 说明 | 适用场景 | 示例 |
|------|------|----------|------|
| **串行流水线** | A→B→C 顺序执行 | 有强依赖关系 | FS→UA→RTL |
| **并行扇出** | A→(B, C, D) 并行执行 | 无依赖关系 | CDC/LP/Reliability 并行 |
| **汇聚合并** | (B, C, D)→E 汇聚 | 需要综合输入 | 专项 Agent 输出→DSE |
| **循环迭代** | A→B→A→B 直到达标 | 需要反复优化 | RTL→Lint→修复→Lint |
| **条件分支** | A→(条件?B:C) | 根据条件选择路径 | 有 CDC?→CDC Agent:跳过 |

### 2.2 协作模式选择决策树

```
多个 Agent 需要执行？
├─ 有依赖关系？
│  ├─ 是 → 串行流水线
│  └─ 否 → 并行扇出
├─ 需要综合多 Agent 输出？
│  └─ 是 → 汇聚合并
├─ 需要迭代优化？
│  └─ 是 → 循环迭代
└─ 有条件触发？
   └─ 是 → 条件分支
```

### 2.3 并行执行约束

| 约束 | 说明 |
|------|------|
| **无共享状态** | 并行 Agent 不能修改同一文件 |
| **无循环依赖** | 并行 Agent 间不能有依赖关系 |
| **输出隔离** | 并行 Agent 的输出文件不能重名 |
| **资源竞争** | 并行 Agent 数量 ≤ 3（避免上下文窗口溢出） |

## 3. 错误恢复策略

### 3.1 错误分类

| 错误类型 | 说明 | 严重程度 | 示例 |
|----------|------|----------|------|
| **输入错误** | 上游 Agent 输出有缺陷 | High | FS 端口定义错误 |
| **执行错误** | Agent 自身执行失败 | Critical | Agent 调用超时 |
| **约束违反** | 输出不满足约束条件 | High | PPA 超预算 |
| **一致性错误** | 与其他 Agent 输出冲突 | High | UA 端口与 FS 不一致 |
| **降级触发** | Agent 降级策略被激活 | Medium | Wiki 检索失败 |

### 3.2 恢复策略

| 错误类型 | 恢复策略 | 最大重试 | 降级方案 |
|----------|----------|----------|----------|
| 输入错误 | 反馈给上游 Agent 修复 | 3 次 | 暂停，等待用户确认 |
| 执行错误 | 重新执行 Agent | 2 次 | 内化执行，标注 `[AGENT-DEGRADED]` |
| 约束违反 | 调整输出或放宽约束 | 2 次 | 暂停，等待用户确认约束调整 |
| 一致性错误 | 以 FS 为 single source，调整下游 | 1 次 | 暂停，报告冲突详情 |
| 降级触发 | 使用降级方案继续 | 0 次 | 直接降级，记录降级原因 |

### 3.3 恢复流程

```
错误发生
  ├─ 可自动恢复？
  │  ├─ 是 → 执行恢复策略 → 验证恢复结果
  │  │  ├─ 恢复成功 → 继续执行
  │  │  └─ 恢复失败 → 升级为不可恢复
  │  └─ 否 → 标记为不可恢复
  └─ 不可恢复？
     ├─ 有降级方案？ → 降级执行，标注 [DEGRADED]
     └─ 无降级方案？ → 暂停，等待用户确认
```

## 4. 级联失败处理

### 4.1 级联失败场景

| 场景 | 触发条件 | 影响范围 | 处理方式 |
|------|----------|----------|----------|
| **FS 修改** | FS 端口/需求变更 | UA + RTL + 验证 | 触发变更传播 v2 |
| **UA 修改** | UA 微架构变更 | RTL + 验证 | 触发变更传播 v2 |
| **RTL Bug** | RTL 功能缺陷 | 验证 + 集成 | 触发缺陷反馈闭环 |
| **CDC 遗漏** | CDC 信号未处理 | RTL + 验证 + 芯片 | 触发 CDC 方法论检查 |

### 4.2 级联阻断策略

```
上游 Agent 失败
  ├─ 下游 Agent 尚未开始？
  │  └─ 阻断下游执行，等待上游修复
  ├─ 下游 Agent 已完成？
  │  └─ 标记下游输出为 [UPSTREAM-CHANGED]，触发重新执行
  └─ 下游 Agent 正在执行？
     └─ 通知下游 Agent 暂停，等待上游修复后决定是否继续
```

### 4.3 影响范围评估

| 变更类型 | 影响范围评估 |
|----------|-------------|
| 端口变更 | FS §6 → UA §4 → RTL module 声明 → SVA → TB |
| FSM 变更 | UA §5.3 → RTL FSM → SVA → 验证场景 |
| FIFO 参数 | UA §5.5 → RTL FIFO 实例 → SVA → 综合约束 |
| CBB 集成 | UA §5.6 → RTL 实例化 → SVA → 验证 |
| 需求变更 | PR → FS → BDD → UA → RTL → 验证 → 软件 |

## 5. 编排引擎配置

### 5.1 编排规则

| 规则 | 说明 |
|------|------|
| **自动触发** | 根据 `specialist-orchestration.json` 的 `trigger_condition` 自动触发 |
| **并行执行** | `parallel_group` 相同且无 `dependencies` 的 Agent 可并行 |
| **顺序门控** | `dependencies` 中的 Agent 全部完成后才启动 |
| **可选依赖** | `optional_dependencies` 中的 Agent 可选传递输入 |
| **跳过逻辑** | `trigger_condition` 不满足时跳过，不阻塞 |
| **超时控制** | 单 Agent 等待上限 3 轮对话 |
| **降级处理** | Agent 调用失败 → 内化执行 |

### 5.2 执行监控

| 监控项 | 说明 |
|--------|------|
| **进度追踪** | 各 Agent 的执行状态（pending/running/completed/failed） |
| **耗时统计** | 各 Agent 的执行耗时 |
| **错误统计** | 错误类型和恢复次数 |
| **降级统计** | 降级触发次数和原因 |

## 6. 集成规则

### 6.1 chip-project-lead 集成

- 项目启动时初始化编排引擎
- 按 `specialist-orchestration.json` 管理 Agent 执行顺序
- 监控 Agent 执行状态，处理错误和降级
- 管理级联失败的影响范围和恢复策略
- 生成编排执行报告（各 Agent 耗时、错误、降级统计）

### 6.2 所有 Agent 通用

- 接收上游上下文时执行上下文验证规则
- 执行失败时遵循错误恢复策略
- 输出时生成结构化上下文供下游使用
- 降级执行时标注 `[DEGRADED]` 并记录原因
