# 变更传播规则 v2（全链路）

> 本模板定义芯片设计全流程的变更传播规则，覆盖 REQ→FS→BDD→UA→RTL→验证全链路。
> 供所有芯片 Agent 共同引用，确保上游变更正确级联到下游所有受影响产物。
> v1 仅覆盖 UA→RTL，v2 扩展为全链路。

---

## 1. 变更传播模型

```
REQ 变更
  │
  ├─→ FS 功能描述变更
  │     │
  │     ├─→ BDD 场景变更
  │     │     │
  │     │     ├─→ UVM Sequence 变更
  │     │     └─→ SVA 断言变更
  │     │
  │     ├─→ UA 微架构变更
  │     │     │
  │     │     ├─→ RTL 代码变更
  │     │     │     │
  │     │     │     ├─→ SDC 约束变更
  │     │     │     └─→ TB 变更
  │     │     │
  │     │     └─→ 验证方案变更
  │     │
  │     └─→ 寄存器定义变更
  │           │
  │           ├─→ 驱动代码变更
  │           └─→ 寄存器头文件变更
  │
  └─→ PPA 指标变更
        │
        ├─→ 约束变更（SDC/UPF）
        └─→ 架构方案调整
```

## 3. 变更传播流程

### 3.1 标准流程

```
变更检测 → 影响分析 → 范围确认 → 级联更新 → 质量门禁重跑 → 追溯验证
```

| 步骤 | 操作 | 负责 Agent |
|------|------|-----------|
| 1. 变更检测 | 识别变更源和变更类型 | 变更发起方 |
| 2. 影响分析 | 按 §2 各阶段表判断影响范围 | `chip-project-lead` |
| 3. 范围确认 | Critical 变更暂停等用户确认 | `chip-project-lead` |
| 4. 级联更新 | 按影响范围调用对应 Agent 更新 | 各专业 Agent |
| 5. 质量门禁 | Lint + 综合 + 自检重新执行 | 各专业 Agent |
| 6. 追溯验证 | 确认全链路追溯完整性 | `chip-arch-reviewer` |

### 3.2 变更检测方法

| 方法 | 适用场景 | 命令 |
|------|----------|------|
| 自动检测 | 文档有 git 历史 | `bash .claude/shared/change-detect.sh <doc_path> [base_commit]` |
| 手动检测 | 用户告知变更内容 | 人工对比差异 |
| 评审发现 | 评审过程中发现不一致 | `chip-arch-reviewer` 输出变更建议 |

### 3.3 影响分析规则

**Critical 变更**（必须暂停等确认）：
- 端口增删/位宽变更
- FSM 状态增删/转移变更
- FIFO 深度/位宽变更
- CBB 版本/参数变更
- REQ 增删
- PPA 指标大幅调整

**Major 变更**（自动级联更新）：
- 功能逻辑修改
- 新增/删除 BDD 场景
- 寄存器位域调整
- 验证方案调整

**Minor 变更**（仅重跑门禁）：
- 描述性内容修改
- 注释优化
- 代码重构（功能不变）
- REQ 优先级调整

## 4. 跨域变更传播

### 4.1 硬件→软件传播

| 硬件变更 | 软件影响 | 触发行为 |
|----------|----------|----------|
| 寄存器地址变更 | 驱动代码 + 头文件 | **强制更新** |
| 寄存器位域变更 | 驱动代码 + 头文件 | **强制更新** |
| 新增寄存器 | 驱动代码 + 头文件 | **新增驱动** |
| 中断信号变更 | 中断处理代码 | **强制更新** |
| 接口协议变更 | 驱动代码 | **强制更新** |

**负责 Agent**：`chip-sw-driver`（架构）、`chip-firmware-writer`（实现）

### 4.2 软件→硬件传播

| 软件需求 | 硬件影响 | 触发行为 |
|----------|----------|----------|
| 新增驱动 API | 寄存器/功能模块 | **评估硬件支持** |
| 性能瓶颈反馈 | 架构优化 | **评估可行性** |
| 功能扩展请求 | FS + UA + RTL | **需求评审** |

**负责 Agent**：`chip-project-lead`（协调）

### 4.3 验证→设计传播

| 验证发现 | 设计影响 | 触发行为 |
|----------|----------|----------|
| RTL Bug | RTL 代码 | **Bug 修复 + 回归** |
| 覆盖率缺口 | BDD 场景 + 验证方案 | **补充场景** |
| 时序违例 | RTL + SDC | **优化修复** |
| 功耗超标 | 架构方案 | **架构调整** |

## 5. 版本号更新规则

| 变更类型 | 版本段 | 示例 |
|----------|--------|------|
| REQ 增删 / 端口变更 / FSM 变更 | major +1 | v1.0 → v2.0 |
| 新增功能 / 修改逻辑 / 新增 BDD 场景 | minor +1 | v1.0 → v1.1 |
| Bug 修复 / 注释优化 / 格式调整 | patch +1 | v1.0 → v1.0.1 |

**级联版本更新**：上游 major 变更时，下游所有受影响文档至少 minor +1。

## 7. 与 v1 的兼容性

| 对比项 | v1 | v2 |
|--------|----|----|
| 覆盖范围 | UA→RTL | REQ→FS→BDD→UA→RTL→验证→软件 |
| 变更源 | 仅微架构文档 | 全链路所有文档 |
| 影响分析 | 单向（UA→RTL） | 双向（正向传播 + 反向反馈） |
| 跨域支持 | 无 | 硬件↔软件、验证→设计 |
| Agent 覆盖 | chip-code-writer | 所有芯片 Agent |
| 版本规则 | 有 | 保留 + 级联更新规则 |

**迁移说明**：v2 完全兼容 v1，v1 的所有规则在 v2 中仍然有效。Agent 引用时统一指向 v2。
