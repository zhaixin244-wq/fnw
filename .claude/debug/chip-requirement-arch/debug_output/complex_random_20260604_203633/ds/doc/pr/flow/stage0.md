## [STAGE-START] stage0 - 前置探索

### 轮 1

**苏启辰**：

GPU Shader Core 是一个极其复杂的模块，预估 75000 行 RTL，预期 55 个 REQ。在正式进入需求采集前，我们需要先厘清几个关键方向性问题。

**第一个问题：模块边界与职责定位**

根据你提供的上下文信息，GPU Shader Core 的位置是"GPU 计算单元"，上游是"GPU 命令处理器"，下游是"共享 L2 缓存/显存控制器"。特性包括 SIMD 执行、纹理采样、光栅化、Tensor Core。

但这里有一个关键问题需要确认：

**在 SoC 架构中，GPU Shader Core 的职责边界如何划分？**

具体来说，有以下三种常见的架构定位方案：

| 方案 | 定位 | 典型特征 |
|------|------|----------|
| **方案 A：纯计算引擎** | Shader Core 仅负责指令译码 + SIMD 执行单元 + 寄存器文件 | 纹理单元、光栅化后端、Tensor Core 作为独立子模块挂在 Shader Core 外部 |
| **方案 B：集成计算+纹理** | Shader Core 包含 SIMD 执行 + 纹理采样单元 | 光栅化后端独立，Tensor Core 可选集成 |
| **方案 C：全集成方案** | Shader Core 包含 SIMD + 纹理 + 光栅化后端 + Tensor Core | 高集成度，内部子模块间通过 NoC 或共享总线互联 |

请问你倾向哪种方案？或者你有其他定义？

这个问题的答案将直接影响：
- 子模块划分的数量和粒度
- 内部数据通路的复杂度
- SRAM/寄存器文件的规模
- 最终 RTL 行数估算

**先问边界再问细节** -- 确认了模块边界，我们才能有针对性地探索后续需求。

**用户**：
方案 C 全集成。GPU Shader Core 必须包含 SIMD 执行单元、纹理采样、光栅化后端和 Tensor Core，这些是现代 GPU 的标配。但你提到内部用 NoC 或共享总线互联，这两种方案的延迟和面积差异你考虑过吗？NoC 路由开销大但可扩展，共享总线简单但会成为瓶颈。75000 行 RTL 的规模下，你建议哪种？为什么？

### 轮 2

**苏启辰**：

**NoC vs 共享总线 vs 混合方案 对比分析**

| 维度 | NoC | 共享总线 | 混合方案 |
|------|-----|----------|----------|
| **面积开销** | +15%~25%（路由节点+缓冲） | +3%~5%（仲裁器+MUX） | +8%~12% |
| **延迟** | 2~5 cycles（多跳路由） | 1~2 cycles（固定仲裁） | 1~3 cycles（按通路分级） |
| **带宽** | 高（多对多并发） | 受限（单次单事务） | 高（关键通路专用） |
| **可扩展性** | 优秀 | 差 | 良好 |
| **设计复杂度** | 高（路由算法+死锁避免） | 低 | 中等 |
| **验证复杂度** | 高 | 低 | 中等 |

**建议：混合方案**

对于 75000 行 RTL 的 GPU Shader Core，建议混合方案，理由如下：

关键数据通路（点对点直连）：
- SIMD 执行单元 → 寄存器文件：每周期需要读取多个操作数，延迟要求极高（1 cycle），必须直连
- 纹理采样单元 → L2 缓存：突发数据流，带宽要求高，专用数据通路
- Tensor Core → 寄存器文件：矩阵运算需要连续数据流，专用通路避免竞争

控制/配置通道（共享总线）：
- 指令分发、状态查询、配置写入：低频、低带宽需求
- 共享总线足够，面积开销小

数据说明：共享总线在子模块超过 6 个时会成为瓶颈。GPU Shader Core 典型包含 8~16 个子模块，纯共享总线方案在满负载时吞吐会下降 30%~40%。

**结论**：混合方案在面积增加约 10% 的前提下，可以获得接近 NoC 的性能，同时设计复杂度可控。

**用户**：
混合方案合理。

### 轮 3

**苏启辰**：

**第二个方向性问题：执行模型与并行度**

GPU Shader Core 的执行模型直接决定 SIMD 宽度、warp/wavefront 数量、调度策略。常见的执行模型有：

| 方案 | 执行模型 | 典型特征 |
|------|----------|----------|
| **方案 A：SIMT（单指令多线程）** | 类似 NVIDIA CUDA Core | warp 调度 + 隐式线程同步 + 分支发散处理 |
| **方案 B：SIMD（单指令多数据）** | 类似 AMD GCN/RDNA | wavefront 执行 + 显式向量操作 + 标量/向量分离 |
| **方案 C：混合 SIMT+SIMD** | 类似现代 GPU | warp 级 SIMT + 向量级 SIMD + Tensor Core 独立执行 |

并行度方面：
- Warp/Wavefront 数量：8 / 16 / 32 / 64？
- SIMD 宽度：32 / 64 / 128 lanes？
- Tensor Core 维度：4x4 / 8x8 / 16x16？

**用户**：
线程模型选 B1 SIMT，SIMD 宽度选 A3 128-wide，对标 NVIDIA Hopper。每线程 128 个 32-bit 寄存器，集中式寄存器文件。但你有没有考虑过 128-wide SIMD 对寄存器文件带宽的压力？

### 轮 4

**苏启辰**：

**寄存器文件带宽分析与 Operand Collector 方案**

128-wide SIMD 对寄存器文件的带宽压力确实是核心挑战。以每线程 128 个 32-bit 寄存器计算：

| 维度 | 数值 | 说明 |
|------|------|------|
| 每 warp 寄存器总量 | 128 threads x 128 regs x 4B = 64 KB | 单个 warp 的寄存器文件容量 |
| 每周期操作数需求 | 128 lanes x 3 operands x 4B = 1536 B/cycle | 三操作数指令的峰值带宽 |
| 寄存器 bank 数 | 32 banks | Operand Collector 标配 |
| 每 bank 带宽 | 48 B/cycle | 1536 / 32 |

**建议：Operand Collector 架构（对标 Hopper）**

| 组件 | 配置 | 说明 |
|------|------|------|
| 寄存器文件 | 32 banks，交叉开关 | 支持 32 个 warp 并行访问 |
| Operand Collector | 每 sub-partition 4 个 collector | 缓存操作数，减少 bank 冲突 |
| 交叉开关 | 128x32 全交叉 | 每个 lane 可访问任意 bank |

面积预估：寄存器文件约 0.4mm²（5nm），Operand Collector 约 0.15mm²，合计 0.55mm²，占总面积约束的 18%。

**SIMD 内部组织方式**

| 方案 | 组织 | 优势 | 劣势 |
|------|------|------|------|
| **方案 A：单一 128-wide** | 1 个 128-wide SIMD 单元 | 设计简单 | 分支发散惩罚大，利用率低 |
| **方案 B：4x32 sub-partition** | 4 个 32-wide sub-partition | 分支发散粒度细，利用率高 | 控制逻辑复杂 |

建议方案 B（4x32 sub-partition），理由：
- 分支发散时，4 个 sub-partition 可以独立执行不同路径
- 每个 sub-partition 有独立的 Operand Collector，减少 bank 冲突
- 对标 Hopper 的 SM 架构

**Tensor Core 配置**

| 方案 | 配置 | 说明 |
|------|------|------|
| **方案 A：FP16 only** | 16x16 FP16 矩阵乘 | 面积小，功能受限 |
| **方案 B：FP16+INT8** | 16x16 FP16/INT8 | 支持推理场景 |
| **方案 C：FP8+FP16+INT8** | 16x16 多精度 | 对标 Hopper，支持 FP8 |

建议方案 C，理由：
- FP8 是 AI 推理的趋势（Hopper H100 标配）
- 多精度复用同一数据通路，面积增量约 30%
- Tensor Core 面积预估 0.2mm²（5nm）

**用户**：
Operand Collector 方案合理。SIMD 组织选方案 B，4x32-wide sub-partition，对标 Hopper。Tensor Core 选方案 C，支持 FP8，对标 Hopper 级别。不过你有没有考虑过 Tensor Core 和 SIMD 执行单元之间的数据搬运开销？Tensor Core 需要从寄存器文件读取矩阵数据，这个带宽需求和 SIMD 的带宽需求会不会冲突？另外 Warp Scheduler 的设计你也该提一下了。

### 轮 5

**苏启辰**：

**TC/SIMD 带宽冲突分析与解决方案**

| 维度 | SIMD 带宽需求 | Tensor Core 带宽需求 | 冲突风险 |
|------|--------------|---------------------|----------|
| 每周期操作数 | 128 lanes x 3 x 4B = 1536 B | 16x16 x 2B (FP16) x 2 = 1024 B | 中等 |
| 访问模式 | 随机（寄存器索引） | 连续（矩阵行/列） | 低（访问模式不同） |
| 峰值叠加 | 1536 B | 1024 B | 2560 B/cycle |

**建议：共享 Operand Collector + TC 专用端口**

| 方案 | 配置 | 面积 | 带宽 | 冲突 |
|------|------|------|------|------|
| **方案 A：完全独立** | TC 独立寄存器文件 | +0.3mm² | 充足 | 无 |
| **方案 B：共享+专用端口** | 共享 Operand Collector，TC 有 2 个专用读端口 | +0.08mm² | 充足 | 低 |
| **方案 C：完全共享** | 无专用端口 | +0 | 受限 | 高 |

建议方案 B，理由：
- 面积增量仅 0.08mm²（5nm）
- TC 专用端口保证矩阵运算不被 SIMD 阻塞
- 共享 Operand Collector 减少数据搬运
- 访问模式不同（TC 连续 vs SIMD 随机），bank 冲突概率低

**Warp Scheduler 设计方案**

| 维度 | 配置 | 说明 |
|------|------|------|
| Warp 数量 | 64 warps | 对标 Hopper，最大化延迟隐藏 |
| 调度策略 | 两级调度 | L1：warp 级优先级；L2：指令级依赖检查 |
| 分支发散处理 | PDOM（Post-Dominator） | 支持任意嵌套分支 |
| 记分板 | 每 warp 独立记分板 | 跟踪寄存器依赖和功能单元占用 |
| 优先级 | Ready > Stall > Sleep | 优先调度就绪 warp |

两级调度详解：
- L1 调度器：从 64 个 warp 中选择候选 warp（基于优先级和状态）
- L2 调度器：从候选 warp 中选择最终执行的 warp（基于指令依赖和功能单元可用性）

面积预估：Warp Scheduler 约 0.1mm²（5nm），记分板约 0.05mm²。

**注意**：warp 数量 64 需要在 stageB 确认，因为它直接影响寄存器文件容量和面积。64 warps x 128 threads x 128 regs x 4B = 4MB 寄存器文件，这在 5nm 工艺下面积约 0.8mm²。

**用户**：
方案 C 和 Warp Scheduler 设计都合理。不过你提到 warp 数量 64 需要在 stageB 确认，这个我先给你约束：面积预算控制在 3mm² 以内（5nm），功耗预算 500mW 以内。warp 数量在这个约束下你自己权衡。另外纹理采样单元的配置你还没提，纹理单元的 cache 结构和采样并发度也需要确认。进入 stageA 吧。
